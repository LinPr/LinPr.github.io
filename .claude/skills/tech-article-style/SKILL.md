# 技术文章的行文规范

适用于本站 `content/posts/` 下的长文，尤其是源码解读（如 scheduler-plugins 系列）。目标读者是有经验的工程师，时间有限，希望扫读时能抓住结论，细读时能看到依据。

改写的边界：**只调整结构、顺序和表述，不改变技术事实**。代码块、图片、标题编号、链接一律保留。

## 一、段落之间要承上启下

模块与模块、小节与小节之间必须有过渡句。读者不应该在读到新标题时还要回想「上一节说了什么、这一节为什么要看」。

**每个小节的第一段做两件事**：回指上一节的结论（一句话），点明本节要回答的问题。

不好的写法（直接开始讲代码）：

> ```go
> func (pl *TaintToleration) EventsToRegister(...)
> ```

好的写法：

> 前面看到，Filter 只在调度周期里判断一次节点能不能用。但被拒绝的 Pod 不会立刻重试，它要等一个「可能已经变了」的信号——这个信号由 `EventsToRegister` 声明，由 QueueingHint 判断。这一节看 TaintToleration 声明了什么、怎么判断。

**每个模块级章节（`##`）的结尾**用一句话收束，并引出下一节。例如：

> 到这里，过滤阶段的两个插件都讲完了：一个看节点自身的开关，一个看节点上的污点。两者都不关心 Pod 之间怎么互相影响，而下一节的 `NodeAffinity` 开始，判定依据第一次来自 Pod 自己的声明。

**避免空转式过渡**：「接下来我们看下一个插件」「下面详细说明」这类话没有信息量，不要用。过渡句必须带具体的对象和下一步的问题。

## 二、重点语句要能一眼看到

- 每个 `###` 小节**最多 1~2 处加粗**，加粗的是**结论、反直觉的事实、或者决定后续行为的规则**，不是名词短语。
- 加粗优先给这几类句子：
  - 一条判定规则（「**只有同时满足三个条件才会返回 `Unschedulable`**」）；
  - 一个容易误解的事实（「**写了 `spec.nodeName` 的 Pod 平时根本不进调度队列**」）；
  - 一个失败码的含义（「**这个错误码决定了抢占能否解决它**」）；
  - 一句总结（「**换句话说，hint 只排除明显无关的事件，不预测调度结果**」）。
- 不要给代码标识符加粗（代码本身已经是等宽字体，再加粗只是噪音）；不要把整句整段的每个名词都加粗。
- 代码块之后的第一句解释，通常是这一段最该加粗的位置：读者刚看完代码，需要一个结论把它收拢。

## 三、段落内部要有结构

**单段不超过 4 行**（中文约 120 字）。超过就拆，或者改写成列表。

一段文字里如果出现「三个要点」「两种返回码」「四种情况」这类计数，先说出数量，再列出：

> 这个判断有两条分支，区别在于节点是被调度器主动关闭的，还是被管理员打了污点。

下面用有序列表展开，每一项一行结论加一句解释。并列、对比、枚举一律用列表或表格，不要揉进一段话。

**每个小节遵循「结论先行」**：

1. 第一句给出结论或本节要回答的问题；
2. 中间是依据（代码、数据、算例）；
3. 最后一句解释「为什么这样设计」或「踩过的坑」。

**该用表格的地方**：多个插件、多个失败码、多个策略、多个参数之间的对比。表格比连续段落更容易扫读。

**算例要分步**：给出输入、按步骤算出中间值、最后给结果，每一步单独一行，不要写成一段话。

## 四、术语：代码里是什么就写什么

不要给代码里的概念另起中文名。读者排查问题时要搜的是代码里的词，不是我们的译名。

| 不要写 | 写成 |
| --- | --- |
| 闸门、门禁 | gate（`PreEnqueue` 这道 gate、gated 状态） |
| 实体 | entity（`QueuedEntityInfo`） |
| 账本、记账 | 用量记录、统计、计数、计量（按句意选，不要一律套一个词） |
| 骨架 | 实现、结构、流程 |
| 计数器 | 计数 |
| 门控 | 校验、gate（feature gate 除外，那是社区通用译法） |

反过来，这些已经是社区或代码里的通用说法，直接用中文写：指纹（`podfingerprint`）、装箱、打散、水位、哨兵值、快照、污点、容忍、准入。

中英文之间留一个空格：「之前的 gate」「进 entity 之前」，不要写成「之前的gate」。

判断标准只有一条：**这个词读者会拿去搜代码或搜报错信息吗？** 会，就保持代码里的写法。

## 五、代码块：带行号，正文引用行号

每篇的代码块都要能「指得到」：读者读到一个结论，能立刻在旁边的代码里找到对应的几行。

- 围栏一律带行号：```` ```go {linenos=inline} ````、```` ```yaml {linenos=inline} ````、```` ```text {linenos=inline} ````。
- 行号是**文章里代码块的行号**，从 1 开始，第一行通常是 `// pkg/...` 路径注释。不要引用源码仓库里的行号，那里随时会变。
- 正文讲到具体逻辑时引用行号：「`PreEnqueue`（第 8–16 行）」「`p.Spec.SchedulingGates` 为空时返回 `nil`（第 9–11 行）」。只给需要定位的地方标，一段话最多一处，不要每句都带。
- 引用前先数一遍，空行也算一行；范围要覆盖完整语句。

**正文里的名字必须来自代码**。不给变量、字段、函数、返回码另起中文名或简称：

| 正文不要写 | 按代码写 |
| --- | --- |
| gate 非空就返回 `UnschedulableAndUnresolvable` | `p.Spec.SchedulingGates` 非空时返回 `UnschedulableAndUnresolvable` |
| 请求量 | `podRequests`、`NodeInfo.Requested`（按上下文选代码里那个） |
| 打分器 | `resourceAllocationScorer` |

判断标准只有一条：读者拿这句话去代码里搜，能不能搜到同一个词。搜不到，就按代码改。

**讲代码执行步骤时一律分点**。一段话里串了「先……再……然后返回……」，或者一句里挂了两个以上行号引用，就拆成有序列表，一步一条、每条带自己的行号：

> `PreEnqueue`（第 8–16 行）分三步：
>
> 1. `p.Spec.SchedulingGates` 为空时直接返回 `nil`，放行（第 9–11 行）；
> 2. 非空时，把每个 gate 的 `Name` 收集到 `gates` 切片（第 12–15 行）；
> 3. 返回 `UnschedulableAndUnresolvable`，消息里用 `%v` 列出这些名字（第 16 行）。

**贴完代码必须用自己的话总结**。代码是佐证，不是结论；读者读到一个代码块，下一段就应该拿到它说了什么，而不是自己去读英文注释或反推逻辑。整块都是上游注释的代码块尤其如此——注释是写给 Kubernetes 开发者看的，读者要的是中文的机制说明。

不好的写法：贴完 `PriorityQueue` 那段「two sub queues and an additional data structure」的注释，下一段直接写「注意注释的措辞：……」，三个队列各干什么还得读者从英文里自己提炼。

好的写法：先用编号列表把注释讲的事逐条说清（谁、做什么、什么时候、为什么），再用一段话点出措辞或设计上的讲究。

**结论不能凭空冒出来**。写「所以……几乎总是为真」「显然不会……」之前，先交代让它成立的机制：谁、在哪、怎么做到的。

不好的写法：「kubelet 只接收 `spec.nodeName` 等于自己的 Pod，所以 `nodename.Fits` 几乎总是为真。」读者会问：kubelet 怎么做到只接收自己的 Pod？

好的写法：先说 kubelet 的 ListWatch 带了字段选择器 `spec.nodeName=<本节点名>`，在 apiserver 端过滤；静态 Pod 由 kubelet 自己写入 `nodeName`；再对照 `Fits` 的判断条件，得出「几乎总是为真」。涉及其他组件时，给出源码文件和函数名。

**流程性强的机制配一个走查例子**。讲完一段多步骤的处理逻辑后，用一个具体对象走一遍：「原本是什么样 → 第 1 步之后变成什么 → …… → 最终结果」。对象要具体到字段取值（Pod 叫什么、`spec.nodeName` 是什么、节点上已用多少 CPU），每一步写清楚哪个函数或哪一行改变了什么。

1. 适合加例子的：队列流转、状态机、多插件合并结果、打分归一化、抢占选 victims、PodGroup 逐个试放、缓存 assume/forget 这类「读完代码仍想不出实际效果」的地方；
2. 不需要加的：一步就能说清的判断、已经有算例或算例图的地方；
3. 例子里的数字和结论必须能从代码推出来，不能为了好讲而编造行为。

**并列条目也用有序列表**。无序列表在长文里读起来是一团，读者数不清有几条、也记不住看到第几条。除非列表本身是嵌套子项，否则一律写成 `1. 2. 3.`，并在引导句里点明数量。

**不写关于「写作过程」的废话**。下面这些话对读者没有信息量，删掉：

- 「全部代码一次可以读完」「代码很短」「只有二十行」这类评价阅读难度的句子（代码长度本身可以用，比如「插件二十行」是事实，「一次可以读完」是谁都能看出的事）；
- 「值得说明」「值得一提」「需要说明的是」「这里不再赘述」这类只起过渡作用的套话，直接说内容；
- 「接下来我们看」「下面就来分析」这类空转引导，用「下一节看什么」替代；
- 对自己的评价：「这一节写得比较细」「篇幅所限」。

判断标准：这句话删掉之后，读者是否丢失了任何关于调度器的信息？丢失了才保留。

## 六、改写时的检查清单

- 每个 `###` 的第一段是否回指了上文、点明了本节问题？
- 每个 `##` 的结尾是否收束并引出下一节？
- 每个小节加粗是否不超过两处，且都是结论而不是名词？
- 有没有超过 4 行的段落？有没有该用列表却写成「首先……其次……最后……」的句子？
- 对比类内容是否做成了表格？
- 代码块是否与原文完全一致（不得改动一个字符）？
- 事实是否与原文、与本地源码一致？拿不准的地方保持原样，不要为了通顺而改动事实。
- 标题编号、图片 shortcode、内部链接是否都保留了？
- 是否引入了对话痕迹（「你提到」「用户要求」）或个人经历？不允许。

## 七、改写手法小结

| 问题 | 手法 |
| --- | --- |
| 直接甩代码 | 先用一句话说清这段代码要解决什么问题，再贴代码 |
| 一段话讲三件事 | 拆成三段，或改成三条列表 |
| 结论埋在段尾 | 移到段首，先给结论再给依据 |
| 术语突然出现 | 第一次出现时用半句话交代它是什么 |
| 小节之间断裂 | 上一节末尾引出问题，下一节开头回指结论 |
| 全篇平铺直叙 | 每个模块结尾用一句话升级问题：「那如果……呢？」 |

# 技术文章的行文规范

适用于本站 `content/posts/` 下的长文，尤其是源码解读（如 scheduler-plugins 系列）。目标读者是有经验的工程师，时间有限，希望扫读时能抓住结论，细读时能看到依据。

改写的边界：**只调整结构、顺序和表述，不改变技术事实**。代码块、图片、标题编号、链接一律保留。

## 一、段落之间要承上启下

模块与模块、小节与小节之间必须有过渡句。读者不应该在读到新标题时还要回想「上一节说了什么、这一节为什么要看」。

**每个小节的第一段做两件事**：回指上一节的结论（一句话），点明本节要回答的问题。

不好的写法（直接开始讲代码）：

> ```go
> func (pl *TaintToleration) EventsToRegister(...)
> ```

好的写法：

> 前面看到，Filter 只在调度周期里判断一次节点能不能用。但被拒绝的 Pod 不会立刻重试，它要等一个「可能已经变了」的信号——这个信号由 `EventsToRegister` 声明，由 QueueingHint 判断。这一节看 TaintToleration 声明了什么、怎么判断。

**每个模块级章节（`##`）的结尾**用一句话收束，并引出下一节。例如：

> 到这里，过滤阶段的两个插件都讲完了：一个看节点自身的开关，一个看节点上的污点。两者都不关心 Pod 之间怎么互相影响，而下一节的 `NodeAffinity` 开始，判定依据第一次来自 Pod 自己的声明。

**避免空转式过渡**：「接下来我们看下一个插件」「下面详细说明」这类话没有信息量，不要用。过渡句必须带具体的对象和下一步的问题。

## 二、重点语句要能一眼看到

- 每个 `###` 小节**最多 1~2 处加粗**，加粗的是**结论、反直觉的事实、或者决定后续行为的规则**，不是名词短语。
- 加粗优先给这几类句子：
  - 一条判定规则（「**只有同时满足三个条件才会返回 `Unschedulable`**」）；
  - 一个容易误解的事实（「**写了 `spec.nodeName` 的 Pod 平时根本不进调度队列**」）；
  - 一个失败码的含义（「**这个错误码决定了抢占能否解决它**」）；
  - 一句总结（「**换句话说，hint 只排除明显无关的事件，不预测调度结果**」）。
- 不要给代码标识符加粗（代码本身已经是等宽字体，再加粗只是噪音）；不要把整句整段的每个名词都加粗。
- 代码块之后的第一句解释，通常是这一段最该加粗的位置：读者刚看完代码，需要一个结论把它收拢。

## 三、段落内部要有结构

**单段不超过 4 行**（中文约 120 字）。超过就拆，或者改写成列表。

一段文字里如果出现「三个要点」「两种返回码」「四种情况」这类计数，先说出数量，再列出：

> 这个判断有两条分支，区别在于节点是被调度器主动关闭的，还是被管理员打了污点。

下面用有序列表展开，每一项一行结论加一句解释。并列、对比、枚举一律用列表或表格，不要揉进一段话。

**每个小节遵循「结论先行」**：

1. 第一句给出结论或本节要回答的问题；
2. 中间是依据（代码、数据、算例）；
3. 最后一句解释「为什么这样设计」或「踩过的坑」。

**该用表格的地方**：多个插件、多个失败码、多个策略、多个参数之间的对比。表格比连续段落更容易扫读。

**算例要分步**：给出输入、按步骤算出中间值、最后给结果，每一步单独一行，不要写成一段话。

## 四、术语：代码里是什么就写什么

不要给代码里的概念另起中文名。读者排查问题时要搜的是代码里的词，不是我们的译名。

| 不要写 | 写成 |
| --- | --- |
| 闸门、门禁 | gate（`PreEnqueue` 这道 gate、gated 状态） |
| 实体 | entity（`QueuedEntityInfo`） |
| 账本、记账 | 用量记录、统计、计数、计量（按句意选，不要一律套一个词） |
| 骨架 | 实现、结构、流程 |
| 计数器 | 计数 |
| 门控 | 校验、gate（feature gate 除外，那是社区通用译法） |

反过来，这些已经是社区或代码里的通用说法，直接用中文写：指纹（`podfingerprint`）、装箱、打散、水位、哨兵值、快照、污点、容忍、准入。

中英文之间留一个空格：「之前的 gate」「进 entity 之前」，不要写成「之前的gate」。

判断标准只有一条：**这个词读者会拿去搜代码或搜报错信息吗？** 会，就保持代码里的写法。

## 五、改写时的检查清单

- 每个 `###` 的第一段是否回指了上文、点明了本节问题？
- 每个 `##` 的结尾是否收束并引出下一节？
- 每个小节加粗是否不超过两处，且都是结论而不是名词？
- 有没有超过 4 行的段落？有没有该用列表却写成「首先……其次……最后……」的句子？
- 对比类内容是否做成了表格？
- 代码块是否与原文完全一致（不得改动一个字符）？
- 事实是否与原文、与本地源码一致？拿不准的地方保持原样，不要为了通顺而改动事实。
- 标题编号、图片 shortcode、内部链接是否都保留了？
- 是否引入了对话痕迹（「你提到」「用户要求」）或个人经历？不允许。

## 五、改写手法小结

| 问题 | 手法 |
| --- | --- |
| 直接甩代码 | 先用一句话说清这段代码要解决什么问题，再贴代码 |
| 一段话讲三件事 | 拆成三段，或改成三条列表 |
| 结论埋在段尾 | 移到段首，先给结论再给依据 |
| 术语突然出现 | 第一次出现时用半句话交代它是什么 |
| 小节之间断裂 | 上一节末尾引出问题，下一节开头回指结论 |
| 全篇平铺直叙 | 每个模块结尾用一句话升级问题：「那如果……呢？」 |
